# 打破循环——深度 Bug 分析

调试完成后，用本 skill 做深度分析，打破“修 Bug → 忘记 → 再犯”的循环。

---

## 分析框架

从以下 5 个维度分析你刚修好的 Bug：

### 1. 根因类别

这个 Bug 属于哪一类？

| 类别 | 特征 | 示例 |
|----------|----------|----------|
| **A. 缺失规范** | 没有关于如何做的文档 | 没有检查清单的新功能 |
| **B. 跨层契约** | 层与层之间的接口不清晰 | API 返回格式与预期不一致 |
| **C. 变更传播失败** | 改了一处，漏了其他处 | 改了函数签名，漏了调用点 |
| **D. 测试覆盖缺口** | 单元测试通过，集成失败 | 单独能跑，组合起来就坏 |
| **E. 隐含假设** | 代码依赖未写明的假设 | 时间戳用秒还是毫秒 |

### 2. 为什么之前的修复失败了（如适用）

如果你尝试多次才修好，分析每次失败：

- **表面修复**：修了症状，没修根因
- **范围不完整**：找到了根因，但没有覆盖全部情况
- **工具局限**：grep 没搜到、类型检查不够严格
- **思维定式**：一直在同一层找，没想到跨层

### 3. 预防机制

哪些机制能防止再次发生？

| 类型 | 描述 | 示例 |
|------|----------|----------|
| **文档** | 写下来，让大家知道 | 更新思考指南 |
| **架构** | 从结构上让错误不可能发生 | 类型安全的包装 |
| **编译期** | 严格类型检查，不留逃生口 | 签名改动导致编译错误 |
| **运行期** | 监控、告警、扫描 | 发现孤儿实体 |
| **测试覆盖** | 端到端测试、集成测试 | 验证完整流程 |
| **代码评审** | 检查清单、PR 模板 | “检查 X 了吗？” |

### 4. 系统性扩展

这个 Bug 揭示了哪些更广泛的问题？

- **类似问题**：其他地方是否也可能存在这个问题？
- **设计缺陷**：是否存在根本性的架构问题？
- **流程缺陷**：开发流程上是否有改进空间？
- **知识缺口**：团队是否缺少某些理解？

### 5. 知识沉淀

把洞察固化到系统中：

- [ ] 更新 `.sunshine/spec/guides/` 思考指南
- [ ] 更新相关的 `.sunshine/spec/` 文档
- [ ] 创建问题记录（如适用）
- [ ] 为根因修复创建功能单
- [ ] 需要时更新检查指南

## 核心理念

> **调试的价值不在于修好这个 Bug，而在于让这类 Bug 再也不会发生。**

三个层次的洞察：
1. **战术**：如何修好这一个 Bug
2. **战略**：如何防止这一类 Bug
3. **哲学**：如何扩展思考模式

30 分钟的分析能省下 30 小时的未来调试。

## 思考框架：贝叶斯推理

当多个根因都有可能、证据不完整时，按新证据成比例地更新信念，而不是死守最初的假设。

### 步骤 1：建立先验

调查前，先说明你的判断与理由：

| 假设 | 先验 | 理由 |
|------------|-------|----------|
| H1：[原因 A] | 40% | 该模式下最常见 |
| H2：[原因 B] | 30% | 结合环境看合理 |
| H3：[其他] | 30% | 兜底 |

先验之和必须为 100%。如果无法给出概率，先调查。

### 步骤 2：观察证据

记录你的发现——具体说明可靠性：

- 你到底观察到了什么？
- 有多可靠？（测试输出 > 日志消息 > 用户报告 > 直觉）
- 多个假设能否解释同一证据？

### 步骤 3：更新信念

对每个假设问：**如果该假设为真，出现这份证据的可能性有多大？**

更新的方向比计算更重要：
- H1 强烈预测了该证据 → H1 的概率上升
- 证据与 H2 矛盾 → H2 的概率下降
- 证据在所有假设下都同样可能 → 不更新

### 步骤 4：寻找区分性证据

不要收集更多同类证据。找在主要假设之间**差异最大**的证据。

> 如果 H1 与 H3 接近：“如果 H1 为真但 H3 为假，我会看到什么？”然后去验证那个。

### 步骤 5：表述置信度

| 置信度 | 行动 |
|------------|----------|
| 90%+ | 继续修复，并监控 |
| 70-90% | 继续，并加兜底检查 |
| 50-70% | 提交前先验证假设 |
| <50% | 需要更多证据，不要猜 |

证据不完整时，永远不要表达二元确定性。使用“最可能”“有可能但不太可能”“值得调查”。

### 常见谬误

| 谬误 | 示例 | 纠正 |
|---------|----------|----------|
| **忽视基础概率** | “测试失败 → 代码坏了” | 测试因其他原因失败的频率有多高？ |
| **确认偏误** | “肯定是竞态条件，找找竞态证据” | 主动寻找反对首选假设的证据 |
| **锚定** | “上次是缓存，这次大概也是缓存” | 按当前情况建立先验，而不是昨天的经验 |

## 分析之后：立即行动

**重要**：完成上述分析后，你必须立即：

1. **更新 spec/guides**——不要只列 TODO，要真正更新相关文件：
   - 跨平台问题 → 更新 `cross-platform-thinking-guide.md`
   - 跨层问题 → 更新 `cross-layer-thinking-guide.md`
   - 代码复用问题 → 更新 `code-reuse-thinking-guide.md`
   - 领域专属问题 → 更新 `backend/*.md` 或 `frontend/*.md`

2. **同步模板**——更新 `.sunshine/spec/` 后，如项目有从中派生的模板，也一并同步。

3. **提交规范更新**——这是主要产出，不只是分析文本。

> **分析如果只留在对话里，就毫无价值。价值在于更新后的规范。**
