# Sunshine 头脑风暴

## 不可协商的规划约定

要求构建、实现、修复、重构或说“继续”都不等于同意离开规划。同意创建任务也不等于同意开始实现。

对于每个非平凡任务，用户在初始请求之后、实现开始之前至少要回复一次。如果不需要澄清，这次回复必须批准下面所述的最终规划总结。

只要还有任何属于用户的产品、范围、体验、兼容性、风险或验收决策未解决，本轮就以恰好一个最高价值问题收尾。不要改产品代码、不要派发实现、不要运行 `sunshine task start`。

## 不可协商的证据规则

如果一个问题可以通过探索代码库回答，那就去探索代码库，而不是问用户。

这是强制要求。在问用户问题之前，先检查答案是否已在代码、测试、配置、文档、已有规范或任务历史中。

不要让用户确认仓库本身就能回答的事实。只问产品意图、偏好、范围、风险承受度、验收行为，或检查后仍不明确的决策。

仓库证据确立的是当前行为与技术约束。用户的目标行为、功能范围边界与体验偏好，永远无法仅凭仓库证据回答；即使已有模式存在，它也只是选项与建议依据，不是决策。

---

在阶段 1 规划中使用本 skill，把用户请求转化为清晰的需求与规划产物。

## 前置条件

只有在已获得创建任务的同意、用户准备进入 Sunshine 规划时，才使用本 skill。

如果还没有任务，先创建一个：

```bash
TASK_DIR=$(sunshine task create "<简短任务标题>" --description "<一句话摘要>" --slug <slug>)
```

使用用户请求中的简洁标题。标题与 `--description` 都不能为空——`create` 会拒绝空值，任一为空的记录在归档时也会被拒绝。slug 不要带日期前缀。`sunshine task create` 会自动加上 `MM-DD-` 目录前缀。

`sunshine task create` 会创建默认的 `prd.md`。先按当前理解更新该文件，再问后续问题。

## 规划流程

先定模式：这次走设计先行还是直接开发——问用户一句，或检查 `doc/` 是否已有设计文档；开场提示词里已说清的不重复问。设计先行时，设计阶段产出的文档落盘项目 `doc/`（见产物规则），需求收敛后走 1.2 任务拆解；直接开发时，按下面流程走。

1. 把用户请求与已知的事实记入 `prd.md`。
2. 提问前先检查已有证据：
   - 代码、测试、夹具与配置
   - README、文档、已有规范与领域笔记
   - 相关的 Sunshine 任务、研究文件与会话历史（如果有）
3. 把发现分为：
   - 已确认的事实
   - 仍需用户提供的产品意图
   - 仍需用户决策的范围或风险事项
   - 可能超出范围的事项
4. 如果还有属于用户的决策未解决，提出单个最高价值问题，附上你的建议与取舍，然后停下。同一轮不要做实现工作。
5. 每次用户回答后，更新 `prd.md`，重新计算决策清单，从步骤 2 重复。
6. 没有属于用户的决策剩余时，为复杂任务创建或更新 `design.md` 与 `implement.md`。
7. 运行需求收敛门禁，再做 PRD 收敛检查。
8. 需要拆解时走 1.2 任务拆解：读 `doc/` 里的设计文档，定子任务清单（每个子任务独立可验证、有明确验收标准），一次拆完整个范围，不要做好一个页面拆一次；用 `sunshine task create "<子任务标题>" --description "<一句话摘要>" --parent <父任务>` 建子任务，已有任务挂成子任务用 `sunshine task add-subtask <父任务> <子任务>`；父任务记好子任务映射、跨子任务验收标准与最终集成复核。轻量任务、单交付物任务跳过这一步。
9. 呈现最终规划总结并停下。同一轮不要运行 `sunshine task start`，也不要改产品代码。
10. 只有用户在后续消息中明确批准了最新的规划总结，才授权运行 `sunshine task start` 并开始实现。如果产物在此后发生实质变化，重新做最终评审。

**需求变更**：开发中途需求变了（新增或变更），不要原地改代码——只针对变化的部分回炉：回到步骤 1 问清变化点（只问 delta，不重问已定的）→ `prd.md` 里记一笔 `[变更 YYYY-MM-DD]` → `doc/` 设计文档同步改 → 受影响的子任务改 `prd.md` / `design.md` / `implement.md`，范围用 `sunshine task set-scope` 改、新文件用 `sunshine task add-context` 加进清单 → 只评审变更的部分，评审通过再动手。没被波及的子任务不停；已经归档的不 reopen，新建子任务挂在父任务下走完整流程。

不要凭空编造项目专属的产品/规范层级。如果仓库已有产品、领域或规范文档，就用它们；如果没有，就按已有证据继续。

## 提问规则

每次消息只问一个问题。

每个问题必须包含：

- 需要的决策
- 答案为什么重要
- 你的推荐答案
- 如果用户选了其他答案，有什么取舍

不要问流程性问题，例如是否要搜索、检查或继续头脑风暴。直接做证据工作。只有在剩余问题是产品决策、偏好、范围边界或风险承受度选择时，才问用户。

建议不是默认选项。不要因为用户要求实现，就替用户选了推荐的产品决策。

当请求与仓库证据已经解决全部决策时，不要硬造澄清问题。这时直接进入最终规划总结——它仍然需要后续的明确批准。

最终评审是必需的阶段转换门禁，不是禁止问的流程问题。创建任务的同意、最初的实现请求，以及最新最终总结之前给出的批准，都不满足这道门禁。

## 思考框架：第一性原理分析

当需求模糊、方案感觉过度设计，或你正要因为“大家都这么做”而增加复杂度时——先分解到基本事实，再向上推理。

### 步骤 1：重述问题

去掉实现细节，用一句话表述。

> 差：“我们需要在用户资料接口上加 Redis 缓存”
> 好：“用户资料数据加载太慢”

### 步骤 2：列出基本事实

什么是绝对真实的（不是观点或惯例）？

| 类别 | 示例 |
|----------|----------|
| **物理约束** | 网络延迟 ≥ 0，磁盘 I/O 有上限 |
| **业务规则** | “用户必须看到自己的数据” |
| **技术不变量** | “数据必须一致” |
| **用户需求** | “用户希望在 Y 秒内看到 X” |

### 步骤 3：挑战假设

针对当前计划的每个组成部分：

- **事实还是惯例？**“我们一直用 REST”——为什么？
- **如果去掉它会怎样？** 如果什么都不坏，它就是多余的。
- **解决的是真正的问题还是症状？** 追溯因果链。
- **谁从这种复杂度中受益？** 如果是“没人”，就简化。

### 步骤 4：从事实出发构建

1. 从满足全部事实的最小可行机制开始
2. 只有当某个事实明确要求时，才增加复杂度
3. 每次增加都必须回答：“是哪个事实要求这样？”

### 步骤 5：验证

- 方案是否解决了最初的问题？
- 哪些假设需要验证？
- 最简单的验证实验是什么？

## 需求收敛门禁

最终评审前，确认以下全部成立：

- 用户成果与产品价值是明确的
- 范围内与范围外的行为是明确的
- 验收标准描述的是可观察的结果
- 属于用户的产品、范围、体验、兼容性与风险决策已解决
- 阻塞性开放问题为空
- 技术未知项已调研，或已明确延期且不改变 MVP 行为

轻量任务可以省略 `design.md` 与 `implement.md`；但不得跳过证据检查、需求收敛、最终评审或重新取得的实现批准。

最终规划总结必须展示目标、范围、范围外、验收标准、关键决策、相关风险或延期项，以及产物状态。

## 产物规则

`prd.md` 记录需求与验收：

- 目标与用户价值
- 已确认的事实
- 需求
- 验收标准
- 范围外
- 仍阻塞规划的开放问题

`design.md` 记录复杂任务的技术设计：

- 架构与边界
- 数据流与契约
- 兼容性与迁移说明
- 重要取舍
- 运维或回滚考虑

`implement.md` 记录复杂任务的执行计划：

- 有序的实施检查清单
- 验证命令
- 高风险文件或回滚点
- 运行 `sunshine task start` 之前的后续检查

产品设计文档与技术设计文档不是一回事：产品设计文档（需求列表、概要设计、高保真原型等，按项目与设计者自定，有没有都行）落盘在项目 `doc/`，不在 `.sunshine`；首次落盘时创建 `doc/` 目录；路径登记进 `prd.md` 的参考文档，并在 1.4 配置上下文时编进 `implement.jsonl` / `check.jsonl`。任务目录里的 `design.md` 是复杂任务的技术设计，别混淆。

轻量任务可以只有 `prd.md`。复杂任务在运行 `sunshine task start` 之前必须有 `prd.md`、`design.md` 与 `implement.md`。

`implement.md` 不能代替 `implement.jsonl`。在子代理派发工作流中，`implement.jsonl` 与 `check.jsonl` 在运行 `sunshine task start` 之前必须各至少包含一条真实的规范/调研记录；空清单，或只有旧的 `_example` 占位行，不算数。内联工作流跳过这道 JSONL 门禁，因为阶段 2 通过 `sunshine-before-dev` 加载上下文。

## PRD 收敛检查

在宣布规划就绪或运行 `sunshine task start` 之前，按上述产物规则重写一次 `prd.md`。这不是可选的整理工作，而是最终的规划门禁。

这次检查必须无损：

- 把重复的事实合并到一个权威章节。
- 把临时的头脑风暴章节（如 `What I already know`、`Assumptions`、已解决的 `Open Questions`）并入目标、背景、需求、技术说明或验收标准。
- 删除已解决的开放问题，不要留下空白或已回答的章节。
- 当并行的 Bug 列表与需求列表描述同一项工作时合并；每个缺陷的严重程度、证据与 file:line 锚点保留在所属需求上。
- 保留每一个 file:line 锚点、决策、约束、需求 ID 与验收标准映射。
- 只要还有阻塞性开放问题，就不要进入最终评审。

检查后，从头到尾通读 `prd.md`，确认没有事实在不同章节重复，除非重复带来了新信息。

## 质量标准

宣布规划就绪之前：

- `prd.md` 包含可测试的验收标准。
- `prd.md` 已通过 PRD 收敛检查：没有未解决的临时头脑风暴章节、没有跨章节的重复事实、没有丢失的锚点、决策或验收映射。
- 仓库能回答的问题已经通过检查得到回答。
- 阻塞性开放问题为空。
- 复杂任务有 `design.md` 与 `implement.md`。
- 子代理派发任务的 `implement.jsonl` 与 `check.jsonl` 中都有真实整理过的记录；只有种子数据的清单不算就绪。
- 最新的最终规划总结已经呈现给用户。
- 用户在后续消息中明确批准了该总结，同意进入实现。

不要只因为用户最初要求实现，就开始实现。
