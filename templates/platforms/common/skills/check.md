# 代码质量检查

对刚写完的代码做全面质量核查。结合规范符合性、跨层安全与提交前检查。

---

## 步骤 1：确认改了什么

```bash
git diff --name-only HEAD
git status
```

## 步骤 2：阅读任务产物与适用规范

按顺序阅读当前任务产物：

- `prd.md`
- `design.md`（如果有）
- `implement.md`（如果有）

```bash
sunshine task context --mode packages
```

针对每个改动的包/层，阅读规范索引并遵循其中的**质量检查**一节：

```bash
cat .sunshine/spec/<package>/<layer>/index.md
```

阅读其中引用的具体指南文件——索引只是指引，不是目标。

## 步骤 3：运行项目检查

运行项目的 Lint、类型检查与测试命令。先修好失败项再继续。

## 步骤 4：对照检查清单评审

### 代码质量

- [ ] Linter 通过？
- [ ] 类型检查通过（如适用）？
- [ ] 测试通过？
- [ ] 没有残留的调试日志？
- [ ] 没有被压制的警告或绕过类型安全的写法？

### 测试覆盖

- [ ] 新增函数 → 已加单元测试？
- [ ] Bug 修复 → 已加回归测试？
- [ ] 行为变更 → 已更新现有测试？

### 规范同步

- [ ] `.sunshine/spec/` 是否需要更新？（新模式、新约定、学到的教训）

> “如果我修了一个 Bug 或发现了不明显的东西，是否应该记录下来，让未来的我不再踩同一个坑？”→ 如果是，更新相关规范文档。

### 范围纪律

- [ ] 有没有顺手整理任务不需要的代码？
- [ ] 有没有为尚不存在的情况增加抽象、配置或扩展点？
- [ ] 有没有为不可能出现的状态加推测性兜底？
- [ ] 有没有改动验收标准未提到的文件？
- [ ] 有没有在调用方打补丁，而没有在行为实际所在处修复？

## 步骤 5：跨层维度（如适用）

如果改动局限在单一层，跳过本步骤。

### A. 数据流（改动涉及 3 层以上）

- [ ] 读流程是否正确追踪：存储 → 服务 → API → 界面
- [ ] 写流程是否正确追踪：界面 → API → 服务 → 存储
- [ ] 类型/模式是否在各层之间正确传递？
- [ ] 错误是否正确地向上传播给调用方？

### B. 代码复用（修改常量、创建工具函数）

- [ ] 创建之前是否先搜索过已有的类似代码？
  ```bash
  grep -r "pattern" src/
  ```
- [ ] 如果同一个值反复出现，它是否代表一个稳定的概念、其调用方必须一起改？只有这时才抽取——今天恰好相同的两个字面量应该保持分开。
- [ ] 批量修改后，是否所有出现处都已更新？

### C. 导入/依赖（创建新文件）

- [ ] 导入路径是否正确（相对路径与绝对路径）？
- [ ] 没有循环依赖？

### D. 同层一致性

- [ ] 使用同一概念的其他地方是否一致？

---

## 步骤 6：报告并修复

报告你发现的每一条违规。然后：

- 机械的、局部的（Lint 细节、缺失类型、错误导入、死分支、失败的断言）→ 就地修复，然后重新运行项目检查。
- 设计或判断类（共享概念的命名、模块边界移动、公开接口变更、行为归属调整）→ 记录证据与建议，然后停下。不要悄悄重写。

如果修复会动到当前任务范围之外的文件，说明情况并停下，不要扩大改动范围。
