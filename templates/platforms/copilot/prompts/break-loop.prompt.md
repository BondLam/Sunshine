# 打破循环——深度 Bug 分析

调试完成后，用本命令做深度分析，打破“修 bug → 忘记 → 再犯”的循环。

---

## 分析框架

从以下 5 个维度分析你刚修好的 bug：

### 1. 根因类别

这个 bug 属于哪一类？

| 类别 | 特征 | 示例 |
|----------|-----------------|---------|
| **A. 缺少规范** | 没有文档说明该怎么做 | 没有检查清单的新功能 |
| **B. 跨层契约** | 层与层之间的接口不明确 | API 返回格式与预期不同 |
| **C. 变更传播失败** | 改了一处，漏了其他处 | 改了函数签名，漏了调用点 |
| **D. 测试覆盖缺口** | 单元测试通过，集成失败 | 单独能跑，合起来就坏 |
| **E. 隐含假设** | 代码依赖未写明的假设 | 时间戳的秒与毫秒混淆 |

### 2. 之前的修复为什么失败（如适用）

如果成功之前尝试过多次修复，分析每次失败：

- **表面修复**：修了症状，没修根因
- **范围不完整**：找到了根因，没覆盖全部情况
- **工具局限**：grep 漏掉了，类型检查不够严
- **心智模型**：一直在同一层找，没想到跨层

### 3. 预防机制

什么样的机制能防止再次发生？

| 类型 | 说明 | 示例 |
|------|-------------|---------|
| **文档** | 写下来，让人知道 | 更新思考指南 |
| **架构** | 从结构上让错误不可能发生 | 类型安全的包装 |
| **编译期** | TypeScript strict、不用 any | 改签名就报编译错误 |
| **运行时** | 监控、告警、扫描 | 发现孤立实体 |
| **测试覆盖** | E2E 测试、集成测试 | 验证完整流程 |
| **代码评审** | 检查清单、PR 模板 | “你检查 X 了吗？” |

### 4. 系统性扩展

这个 bug 揭示了哪些更广泛的问题？

- **类似问题**：其他地方是否也存在这个问题？
- **设计缺陷**：是否存在根本性的架构问题？
- **流程缺陷**：开发流程是否有改进空间？
- **知识缺口**：团队是否缺少某些理解？

### 5. 知识沉淀

把洞察固化到系统里：

- [ ] 更新 `.sunshine/spec/guides/` 思考指南
- [ ] 更新 `.sunshine/spec/backend/` 或 `frontend/` 文档
- [ ] 创建问题记录（如适用）
- [ ] 为根因修复创建功能 ticket
- [ ] 按需更新检查命令

---

## 输出格式

请按以下格式输出分析：

```markdown
## Bug 分析：[简短描述]

### 1. 根因类别
- **类别**：[A/B/C/D/E] - [类别名称]
- **具体原因**：[详细描述]

### 2. 之前的修复为什么失败（如适用）
1. [第一次尝试]：[为什么失败]
2. [第二次尝试]：[为什么失败]
...

### 3. 预防机制
| 优先级 | 机制 | 具体行动 | 状态 |
|----------|-----------|-----------------|--------|
| P0 | ... | ... | TODO/DONE |

### 4. 系统性扩展
- **类似问题**：[列出有类似问题的地方]
- **设计改进**：[架构层面的建议]
- **流程改进**：[开发流程方面的建议]

### 5. 知识沉淀
- [ ] [要更新的文档 / 要创建的 ticket]
```

---

## 核心理念

> **调试的价值不在于修好这个 bug，而在于让这类 bug 永远不再发生。**

三个层次的洞察：
1. **战术**：怎么修好**这个** bug
2. **战略**：怎么预防**这类** bug
3. **哲学**：怎么扩展思考模式

30 分钟的分析能省下未来 30 小时的调试。

---

## 分析之后：立即行动

**重要**：完成上述分析后，你必须立即：

1. **更新规范/指南**——不要只列 TODO，要真正更新相关文件：
   - 如果是跨平台问题 → 更新 `cross-platform-thinking-guide.md`
   - 如果是跨层问题 → 更新 `cross-layer-thinking-guide.md`
   - 如果是代码复用问题 → 更新 `code-reuse-thinking-guide.md`
   - 如果是领域相关 → 更新 `backend/*.md` 或 `frontend/*.md`

2. **同步模板**——更新 `.sunshine/spec/` 之后，同步到 `src/templates/markdown/spec/`

3. **提交规范更新**——这是主要产出，不只是分析文本

> **分析如果只留在对话里，就毫无价值。价值在于更新后的规范。**
