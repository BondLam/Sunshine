# 更新代码规范——沉淀可执行契约

当你学到有价值的东西（来自调试、实现或讨论），用本命令更新相关代码规范文档。

**时机**：完成任务、修复 bug 或发现新模式之后

---

## 代码规范优先规则（关键）

在本项目中，实现工作的“规范”指**代码规范**：
- 可执行契约（不只是原则性文字）
- 具体的签名、载荷字段、env 键与边界行为
- 可测试的验证/错误行为

如果改动涉及基础设施或跨层契约，代码规范的深度是强制的。

### 强制触发条件

改动包含以下任一项时，采用代码规范深度：
- 新增/变更命令或 API 签名
- 跨层请求/响应契约变更
- 数据库 schema/迁移变更
- 基础设施集成（存储、队列、缓存、密钥、env 接线）

### 强制输出（7 节）

对触发的任务，包含以下全部章节：
1. 范围 / 触发条件
2. 签名（命令/API/DB）
3. 契约（请求/响应/env）
4. 验证与错误矩阵
5. 好/基准/坏案例
6. 需要的测试（附断言点）
7. 错误 vs 正确（至少一对）

---

## 何时更新代码规范

| 触发条件 | 示例 | 目标规范 |
|---------|---------|-------------|
| **实现了一个功能** | 用 giget 加了模板下载 | 相关 `backend/` 或 `frontend/` 文件 |
| **做了一个设计决策** | 用类型字段 + 映射表换取可扩展性 | 相关代码规范 + “设计决策”章节 |
| **修复了一个 bug** | 发现错误处理的微妙问题 | `backend/error-handling.md` |
| **发现了一个模式** | 找到更好的代码组织方式 | 相关 `backend/` 或 `frontend/` 文件 |
| **踩到了坑** | 学到 X 必须在 Y 之前做 | 相关代码规范 + “常见错误”章节 |
| **确立了一个约定** | 团队就命名模式达成一致 | `quality-guidelines.md` |
| **新的思考触发点** | “做 Y 之前别忘了检查 X” | `guides/*.md`（作为检查清单项，不是详细规则） |

**关键洞察**：代码规范更新不只是为了问题。每次功能实现都包含设计决策与契约，未来的 AI/开发者需要它们才能安全执行。

## 规范结构概览

```
.sunshine/spec/
├── backend/           # 后端编码标准
│   ├── index.md       # 概览与链接
│   └── *.md           # 各主题指南
├── frontend/          # 前端编码标准
│   ├── index.md       # 概览与链接
│   └── *.md           # 各主题指南
└── guides/            # 思考检查清单（不是编码规范！）
    ├── index.md       # 指南索引
    └── *.md           # 各主题指南
```

### 关键：代码规范 vs 指南——分清区别

| 类型 | 位置 | 用途 | 内容风格 |
|------|----------|---------|---------------|
| **代码规范** | `backend/*.md`、`frontend/*.md` | 告诉 AI “如何安全实现” | 签名、契约、矩阵、案例、测试点 |
| **指南** | `guides/*.md` | 帮助 AI “写之前想什么” | 检查清单、问题、指向规范的指针 |

**判断规则**：问自己：

- “这是**怎么写**代码” → 放到 `backend/` 或 `frontend/`
- “这是写之前**要考虑什么**” → 放到 `guides/`

**示例**：

| 学到的东西 | 错误位置 | 正确位置 |
|----------|----------------|------------------|
| “Windows stdout 用 `reconfigure()` 而不是 `TextIOWrapper`” | ❌ `guides/cross-platform-thinking-guide.md` | ✅ `backend/script-conventions.md` |
| “写跨平台代码时记得检查编码” | ❌ `backend/script-conventions.md` | ✅ `guides/cross-platform-thinking-guide.md` |

**指南应该是短检查清单，指向规范**，而不是重复详细规则。

## 更新流程

### 步骤 1：确认你学到了什么

回答这些问题：

1. **你学到了什么？**（具体说明）
2. **为什么重要？**（它预防了什么问题？）
3. **它属于哪里？**（哪个规范文件？）

### 步骤 2：给更新类型分类

| 类型 | 描述 | 动作 |
|---|---|---|
| **设计决策** | 为什么选方案 X 而不是 Y | 加到“设计决策”章节 |
| **项目约定** | 本项目如何做 X | 加到相关章节，附示例 |
| **新模式** | 发现的可复用做法 | 加到“模式”章节 |
| **禁用模式** | 会引发问题的东西 | 加到“反模式”或“不要”章节 |
| **常见错误** | 容易犯的错误 | 加到“常见错误”章节 |
| **约定** | 达成一致的标准 | 加到相关章节 |
| **坑** | 不明显的行为 | 加警告提示 |

### 步骤 3：阅读目标代码规范

编辑之前，先读当前代码规范，以便：
- 理解现有结构
- 避免重复内容
- 找到合适的章节

```bash
cat .sunshine/spec/<category>/<file>.md
```

### 步骤 4：做更新

遵循这些原则：

1. **具体**：给出具体示例，不只是抽象规则
2. **解释原因**：说明它预防了什么问题
3. **展示契约**：加上签名、载荷字段与错误行为
4. **展示代码**：给关键模式加上代码片段
5. **保持简短**：每节一个概念

### 步骤 5：更新索引（如需要）

如果你新增了章节或代码规范状态变了，更新该类别的 `index.md`。

## 更新模板

### 基础设施/跨层工作的强制模板

```markdown
## 场景：<name>

### 1. 范围 / 触发条件
- 触发条件：<为什么需要代码规范深度>

### 2. 签名
- 后端命令/API/DB 签名

### 3. 契约
- 请求字段（名称、类型、约束）
- 响应字段（名称、类型、约束）
- 环境键（必需/可选）

### 4. 验证与错误矩阵
- <条件> -> <错误>

### 5. 好/基准/坏案例
- 好：...
- 基准：...
- 坏：...

### 6. 需要的测试
- 单元/集成/E2E，附断言点

### 7. 错误 vs 正确
#### 错误
...
#### 正确
...
```

### 添加设计决策

```markdown
### 设计决策：[决策名称]

**背景**：要解决什么问题？

**考虑过的选项**：
1. 选项 A——简述
2. 选项 B——简述

**决策**：我们选了选项 X，因为……

**示例**：
\`\`\`typescript
// 如何实现
code example
\`\`\`

**可扩展性**：以后如何扩展……
```

### 添加项目约定

```markdown
### 约定：[约定名称]

**是什么**：约定的简述。

**为什么**：为什么我们这么做。

**示例**：
\`\`\`typescript
// 如何遵守该约定
code example
\`\`\`

**相关**：相关约定与规范的链接。
```

### 添加新模式

```markdown
### 模式名称

**问题**：解决什么问题？

**方案**：简述做法。

**示例**：
\`\`\`
// 好
code example

// 坏
code example
\`\`\`

**为什么**：解释为什么这样做有效。
```

### 添加禁用模式

```markdown
### 不要：模式名称

**问题**：
\`\`\`
// 不要这么做
bad code example
\`\`\`

**为什么不好**：解释原因。

**替代做法**：
\`\`\`
// 这样做
good code example
\`\`\`
```

### 添加常见错误

```markdown
### 常见错误：描述

**症状**：出了什么问题

**原因**：为什么会这样

**修复**：如何纠正

**预防**：如何避免
```

### 添加坑

```markdown
> **警告**：简述不明显的行为。
>
> 详细说明何时发生、如何处理。
```

## 交互模式

如果你不确定要更新什么，回答这些提示：

1. **你刚完成了什么？**
   - [ ] 修复了一个 bug
   - [ ] 实现了一个功能
   - [ ] 重构了代码
   - [ ] 讨论了方案

2. **你学到或决定了什么？**
   - 设计决策（为什么选 X 而不是 Y）
   - 项目约定（本项目如何做 X）
   - 不明显的行为（坑）
   - 更好的做法（模式）

3. **未来的 AI/开发者需要知道吗？**
   - 为了理解代码如何工作 → 是，更新规范
   - 为了维护或扩展功能 → 是，更新规范
   - 为了避免重复犯错 → 是，更新规范
   - 纯粹一次性实现细节 → 也许跳过

4. **它属于哪个领域？**
   - [ ] 后端代码
   - [ ] 前端代码
   - [ ] 跨层数据流
   - [ ] 代码组织/复用
   - [ ] 质量/测试

## 质量检查清单

完成代码规范更新之前：

- [ ] 内容具体、可执行吗？
- [ ] 包含代码示例了吗？
- [ ] 解释了为什么，而不只是是什么吗？
- [ ] 包含可执行签名/契约了吗？
- [ ] 包含验证与错误矩阵了吗？
- [ ] 包含好/基准/坏案例了吗？
- [ ] 包含带断言点的必需测试了吗？
- [ ] 放在正确的代码规范文件里了吗？
- [ ] 有重复内容吗？
- [ ] 新团队成员能看懂吗？

## 与其他命令的关系

```
Development Flow:
  学到东西 → / → 知识已沉淀
       ↓                                 ↓
  / ←──────────────────── 未来会话受益
  （深度 bug 分析）
```

- `/`——深度分析 bug，常常揭示需要更新的规范
- `/`——实际做更新（本命令）
- `/`——提醒你检查规范是否需要更新

---

## 核心理念

> **代码规范是活文档。每次调试、每次“aha moment”，都是让实现契约更清晰的机会。**

目标是**制度记忆**：
- 一个人学到的东西，所有人受益
- AI 在一个会话里学到的东西，沉淀到未来会话
- 错误变成有记录的护栏
