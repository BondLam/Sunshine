# Sunshine 头脑风暴

## 不可协商的规划契约

要求构建、实现、修复、重构，或说一句“继续”，都不是离开规划的许可。创建任务的同意也不是实现许可。

对于每个非平凡任务，在开始实现之前，用户必须在最初请求之后至少回应一次。如果不需要澄清，那次回应必须批准下面所述的最终规划总结。

只要还有任何用户拥有的产品、范围、UX、兼容性、风险或验收决策未解决，回合结束时只能提一个价值最高的问题。不要改产品代码、不要派发实现、不要运行 `sunshine task start`。

## 不可协商的证据规则

如果一个问题可以通过探索代码库回答，那就去探索代码库，不要问用户。

这是强制要求。在问用户问题之前，先检查答案是否已经存在于代码、测试、配置、文档、现有规范或任务历史中。

不要让用户确认仓库本身就能回答的事实。只问产品意图、偏好、范围、风险容忍度，或检查后仍含糊的验收行为。

仓库证据确定当前行为与技术约束。用户的预期行为、功能范围边界与 UX 偏好，永远不能只靠仓库证据回答，即使已有现成模式；现有模式只是选项与建议证据，不是决策。

---

在阶段 1 规划中使用本 skill，把用户请求变成清晰的需求与规划产物。

## 前置条件

只有在已获得创建任务的同意、用户准备进入 Sunshine 规划时，才使用本 skill。

如果还没有任务，先创建一个：

```bash
TASK_DIR=$(sunshine task create "<short task title>" --description "<one-line summary>" --slug <slug>)
```

用用户请求提炼一个简洁标题。标题与 `--description` 都不能为空——`create` 会拒绝空值，任一为空的记录在归档时也会被拒绝。slug 不带日期前缀。`sunshine task create` 会自动加上 `MM-DD-` 目录前缀。

`sunshine task create` 会创建默认的 `prd.md`。在问后续问题之前，先用当前理解更新该文件。

## 规划流程

1. 把用户请求与已知的初始事实记录到 `prd.md`。
2. 在提问之前检查现有证据：
   - 代码、测试、fixture 与配置
   - README、文档、现有规范与领域笔记
   - 已有的相关 Sunshine 任务、调研文件与会话历史
3. 把发现分成：
   - 已确认的事实
   - 仍需用户给出的产品意图
   - 仍需用户决定的范围或风险事项
   - 可能超出范围的事项
4. 如果还有用户拥有的决策未解决，问唯一一个价值最高的问题（按排序规则挑），附上建议与取舍，然后停下。同一回合不要做实现工作。
5. 每次用户回答后，更新 `prd.md`，对照需求维度清单重新计算决策清单，从步骤 2 重复。
6. 没有用户拥有的决策剩下时，为复杂任务创建或更新 `design.md` 与 `implement.md`。
7. 跑需求收敛关卡，然后跑 PRD 收敛检查。
8. 呈现最终规划总结并停下。不要在同一回合运行 `sunshine task start` 或改产品代码。
9. 只有用户在后续消息里明确批准了最新规划总结，才授权 `sunshine task start` 与实现。如果批准后产物发生实质变化，重新走一次最终评审。

不要凭空编造项目专属的产品/规范层级。如果仓库已有产品、领域或规范文档，就用它们。如果没有，就用已有的证据推进。

## 提问规则

每次消息只问一个问题。

每个问题必须包含：

- 需要做的决策
- 答案为什么重要
- 你推荐的答案
- 用户选了其他答案时的取舍

不要问流程性问题，例如是否要搜索、检查文件或继续头脑风暴。证据工作直接做。只有剩下的问题是产品决策、偏好、范围边界或风险容忍度选择时，才问用户。

建议不是默认选项。永远不要因为用户要求实现，就替用户选一个推荐的产品决策。

当请求与仓库证据已经解决所有决策时，不要编造澄清问题。这种情况下直接进入最终规划总结，它仍然需要后续的明确批准。

最终评审是必需的阶段转换关卡，不是被禁止的流程问题。创建任务的同意、最初的实现请求，以及最新最终总结之前给出的批准，都不满足这个关卡。

## 需求维度清单

每轮提问前，对照下面八个维度，看哪个还没覆盖：已确认、已明确划在范围外、不适用，三者之一才算覆盖；其余的进决策清单，下一轮接着问。

| 维度 | 覆盖了算什么 |
| --- | --- |
| 用户与场景 | 谁用、在什么场景下用 |
| 功能边界 | 做什么、不做什么、做到什么程度 |
| 数据 | 数据从哪来、存哪、关键字段 |
| 性能 | 响应、并发、数据量上有什么要求 |
| 安全 | 权限、隐私、敏感数据怎么处理 |
| 兼容性 | 要兼容什么旧行为、旧数据、旧接口 |
| 验收 | 怎么算做完、可观察的结果是什么 |
| 范围外 | 明确不做的事 |

不适用的维度直接标不适用，不用硬问。维度清单只保证不漏，不保证每个问题都问得准；问得准还是靠判断，最终评审兜底。

## 排序规则：哪个问题价值最高

每轮只问一个，从决策清单里按下面顺序挑：

1. 阻塞后续工作的先问——不答没法往下走的；
2. 不可逆的先问——选错了返工成本大的；
3. 成本高的先问——影响范围大的；
4. 枝节后问——细节、偏好、可以后补的。

## 需求收敛关卡

在最终评审之前，确认全部满足：

- 用户结果与产品价值是明确的
- 范围内与范围外的行为是明确的
- 验收标准描述的是可观察的结果
- 用户拥有的产品、范围、UX、兼容性与风险决策已解决
- 阻塞性开放问题为空
- 技术未知项已调研，或已明确延期且不改变 MVP 行为

轻量任务可以省略 `design.md` 与 `implement.md`；但不能跳过证据检查、需求收敛、最终评审或重新获得实现批准。

最终规划总结必须展示目标、范围内、范围外、验收标准、关键决策、相关风险或延期事项，以及产物状态。

## 产物规则

`prd.md` 记录需求与验收：

- 目标与用户价值
- 已确认的事实
- 需求
- 验收标准
- 范围外
- 仍阻塞规划的开放问题

`design.md` 记录复杂任务的技术设计：

- 架构与边界
- 数据流与契约
- 兼容性与迁移说明
- 重要取舍
- 运维或回滚考虑

`implement.md` 记录复杂任务的执行规划：

- 有序实现检查清单
- 验证命令
- 高风险文件或回滚点
- `sunshine task start` 之前的后续检查

轻量任务可以只有 `prd.md`。复杂任务在 `sunshine task start` 之前必须有 `prd.md`、`design.md` 与 `implement.md`。

`implement.md` 不能替代 `implement.jsonl`。在子代理派发工作流中，`sunshine task start` 之前 `implement.jsonl` 与 `check.jsonl` 必须各含至少一条真实规范/调研条目；空清单，或只有旧版 `_example` 占位行的清单，都不算数。内联工作流跳过这个 JSONL 关卡，因为阶段 2 通过 `sunshine-before-dev` 加载上下文。

## PRD 收敛检查

在宣布规划就绪或运行 `sunshine task start` 之前，按上面产物规则所述的最终结构，把 `prd.md` 重写一遍。这不是可选的清理；这是最终规划关卡。

这次检查必须无损：

- 把重复事实合并到唯一权威章节。
- 把 `What I already know`、`Assumptions`、已解决的 `Open Questions` 等临时头脑风暴章节，并入目标、背景、需求、技术说明或验收标准。
- 删除已解决的开放问题，不要留下空白或已回答的章节。
- 合并描述同一工作的并行 bug 列表与需求列表；每个缺陷的严重程度、证据与 file:line 锚点保留在所属需求上。
- 保留每一个 file:line 锚点、决策、约束、需求 ID 与验收标准映射。
- 仍有阻塞性开放问题时，不要进入最终评审。

检查后，从头到尾读一遍 `prd.md`，确认没有事实跨章节重复，除非重复带来了新信息。

## 质量标准

在宣布规划就绪之前：

- `prd.md` 含有可测试的验收标准。
- `prd.md` 已通过 PRD 收敛检查：没有未解决的临时头脑风暴章节，没有跨章节重复事实，没有丢失锚点、决策或验收映射。
- 仓库能回答的问题已经通过检查回答了。
- 阻塞性开放问题为空。
- 复杂任务有 `design.md` 与 `implement.md`。
- 子代理派发任务的 `implement.jsonl` 与 `check.jsonl` 都有真实整理好的条目；只有种子条目的清单不算就绪。
- 最新最终规划总结已呈现给用户。
- 用户在后续消息里明确批准了该总结，同意实现。

不要只因为用户最初要求实现，就开始实现。
