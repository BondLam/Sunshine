## 核心理念：这个工作流为什么存在

AI 辅助开发有三个根本挑战：

### 挑战 1：AI 没有记忆

每个 AI 会话都从空白开始。人类工程师会在几周/几个月里积累项目知识，而 AI 在会话结束时就忘掉一切。

**问题**：没有记忆，AI 会反复问同样的问题、犯同样的错误，无法在之前工作的基础上推进。

**解决办法**：`.sunshine/workspace/` 系统记录每个会话发生的事——做了什么、学到了什么、解决了什么问题。`/` 命令在会话开始时读取这段历史，给 AI 一份“人工记忆”。

### 挑战 2：AI 只有通用知识，没有项目专属知识

AI 模型在数百万代码库上训练过——它们了解 React、TypeScript、数据库等的通用模式。但它们不了解**你们项目**的约定。

**问题**：AI 写的代码“能跑”，但不符合你们项目的风格。它用的模式与现有代码冲突，做的决定违反团队不成文的规则。

**解决办法**：`.sunshine/spec/` 目录放着项目专属指南。`/before-*-dev` 命令在写代码之前把这些专属知识注入 AI 上下文。

### 挑战 3：AI 上下文窗口有限

即使注入了指南，AI 的上下文窗口也是有限的。随着对话增长，早期的上下文（包括指南）会被推出去，或影响力减弱。

**问题**：AI 一开始还遵循指南，但随着会话推进、上下文填满，它会“忘记”规则，退回通用模式。

**解决办法**：`/check-*` 命令在写完代码**之后**对照指南重新验证，捕捉写代码过程中发生的漂移。`/` 命令做最后的整体评审。

## 系统结构

```
.sunshine/
|-- .developer              # 你的身份（gitignored）
|-- workflow.md             # 完整工作流文档
|-- workspace/              # “AI 记忆”——会话历史
|   |-- index.md            # 所有开发者的进度
|   +-- {developer}/        # 每位开发者目录
|       |-- index.md        # 个人进度索引
|       +-- journal-N.md    # 会话记录（最多 2000 行）
|-- tasks/                  # 任务跟踪（统一）
|   +-- {MM}-{DD}-{slug}/   # 任务目录
|       |-- task.json       # 任务元数据
|       +-- prd.md          # 需求文档
|-- spec/                   # “AI 训练数据”——项目知识
|   |-- frontend/           # 前端约定
|   |-- backend/            # 后端约定
|   +-- guides/             # 思考模式
+-- scripts/                # 自动化工具
```

### 理解 spec/ 子目录

**frontend/**——单层前端知识：
- 组件模式（在这个项目里怎么写组件）
- 状态管理规则（Redux？Zustand？Context？）
- 样式约定（CSS modules？Tailwind？Styled-components？）
- Hook 模式（自定义 hook、数据获取）

**backend/**——单层后端知识：
- API 设计模式（REST？GraphQL？tRPC？）
- 数据库约定（查询模式、迁移）
- 错误处理标准
- 日志与监控规则

**guides/**——跨层思考指南：
- 代码复用思考指南
- 跨层思考指南
- 实现前检查清单

## 命令详解

### /——恢复 AI 记忆

**为什么存在**：
人类工程师加入项目时，要花几天/几周学习：这个项目是什么？已经建了什么？正在做什么？当前状态如何？

AI 也需要同样的 onboarding——但要在会话开始的几秒钟内压缩完成。

**实际动作**：
1. 读取开发者身份（我在这个项目里是谁？）
2. 检查 git 状态（哪个分支？有没有未提交的改动？）
3. 从 `workspace/` 读取最近会话历史（之前发生了什么？）
4. 识别进行中的功能（正在做什么？）
5. 在动手之前理解当前项目状态

**为什么重要**：
- 没有 /：AI 是盲目的。它可能在错误的分支上工作、与他人的工作冲突，或重做已经完成的工作。
- 有 /：AI 知道项目上下文，可以从上个会话停下的地方继续，避免冲突。

---

### /——注入专属知识

**为什么存在**：
AI 模型有“预训练知识”——来自数百万代码库的通用模式。但**你们项目**有不同于通用模式的专属约定。

**实际动作**：
1. 通过 `sunshine task context --mode packages` 发现规范层，阅读相关指南
2. 把项目专属模式加载到 AI 的工作上下文：
   - 组件命名约定
   - 状态管理模式
   - 数据库查询模式
   - 错误处理标准

**为什么重要**：
- 没有 before-dev：AI 写的是不符合项目风格的通用代码。
- 有 before-dev：AI 写的代码看起来像代码库其他部分。

---

### /——对抗上下文漂移

**为什么存在**：
AI 上下文窗口容量有限。随着对话推进，会话开始时注入的指南影响力减弱。这就造成了“上下文漂移”。

**实际动作**：
1. 重新阅读之前注入的指南
2. 对照指南比较写好的代码
3. 运行类型检查与 linter
4. 发现违规并提出修复建议

**为什么重要**：
- 没有 check-*：上下文漂移无人察觉，代码质量下降。
- 有 check-*：漂移在提交前被发现并纠正。

---

### /——多维度验证

**为什么存在**：
大多数 bug 不是技术不行造成的——而是“没想到”：
- 在一处改了常量，漏了其他 5 处
- 改了数据库 schema，忘了更新 API 层
- 建了个工具函数，但类似的已经存在

**实际动作**：
1. 确认改动涉及哪些维度
2. 对每个维度做针对性检查：
   - 跨层数据流
   - 代码复用分析
   - 导入路径验证
   - 一致性检查

---

### /——提交前整体评审

**为什么存在**：
`/check-*` 命令关注单层内的代码质量。但真实改动往往有跨切面问题。

**实际动作**：
1. 整体评审所有改动
2. 检查跨层一致性
3. 识别更广泛的影响
4. 检查新模式是否应该记录下来

---

### /——为未来持久化记忆

**为什么存在**：
本会话 AI 积累的所有上下文，在会话结束时都会丢失。下个会话的 `/` 需要这些信息。

**实际动作**：
1. 把会话总结记录到 `workspace/{developer}/journal-N.md`
2. 记录做了什么、学到了什么、还剩下什么
3. 更新索引文件以便快速查找

## 要强调的关键规则

1. **AI 永远不提交**——人测试并批准。AI 准备，人验证。
2. **先有指南，再写代码**——/before-dev 命令注入项目知识。
3. **写完代码要检查**——/check-* 命令发现上下文漂移。
4. **什么都记录下来**——/ 持久化记忆。

# 第三部分：定制你的开发规范

讲完第一部分与第二部分后，检查项目的开发规范是否需要定制。

## 步骤 1：检查当前规范状态

检查 `.sunshine/spec/` 里是空模板还是已定制的规范：

```bash
# 检查文件是否还是空模板（找占位文本）
grep -l "To be filled by the team" .sunshine/spec/backend/*.md 2>/dev/null | wc -l
grep -l "To be filled by the team" .sunshine/spec/frontend/*.md 2>/dev/null | wc -l
```

## 步骤 2：判断情况

**情况 A：首次搭建（空模板）**

如果规范是空模板（含有 “To be filled by the team”），这是项目第一次用 Sunshine。

向开发者解释：

“我看到 `.sunshine/spec/` 里的开发规范还是空模板。这在新搭建的 Sunshine 项目里是正常的！

模板里的占位文本需要替换成**你们项目**真实的约定。没有这一步，`/before-*-dev` 命令提供不了有用的指导。

**你的第一个任务应该是填写这些规范：**

1. 看看现有代码库
2. 识别已经在用的模式与约定
3. 把它们记录到规范文件里

例如，对于 `.sunshine/spec/backend/database-guidelines.md`：
- 你们项目用什么 ORM/查询库？
- 迁移如何管理？
- 表/列的命名约定是什么？

要不要我帮你分析代码库、填写这些规范？”

**情况 B：规范已经定制**

如果规范已有真实内容（没有 “To be filled” 占位符），这是已有搭建。

向开发者解释：

“太好了！你们团队已经定制了开发规范。你现在就可以直接用 `/before-*-dev` 命令了。

我建议通读一遍 `.sunshine/spec/`，熟悉团队的编码标准。”

## 步骤 3：帮忙填写规范（如果是空的）

如果开发者想帮忙填规范，先建一个功能来跟踪：

```bash
sunshine task create "Fill spec guidelines" --description "Fill in the spec guideline files" --slug fill-spec-guidelines
```

然后系统地分析代码库，逐个填写规范文件：

1. **分析代码库**——看现有代码模式
2. **记录约定**——写你观察到的，而不是理想状态
3. **附上示例**——引用真实文件
4. **列出禁用模式**——记录团队避免的反模式

一次处理一个文件：
- `backend/directory-structure.md`
- `backend/database-guidelines.md`
- `backend/error-handling.md`
- `backend/quality-guidelines.md`
- `backend/logging-guidelines.md`
- `frontend/directory-structure.md`
- `frontend/component-guidelines.md`
- `frontend/hook-guidelines.md`
- `frontend/state-management.md`
- `frontend/quality-guidelines.md`
- `frontend/type-safety.md`
