# 代码质量检查

对最近写的代码做全面质量验证。结合规范符合性、跨层安全与提交前检查。

---

## 步骤 1：确认改了什么

```bash
git diff --name-only HEAD
git status
```

## 步骤 2：阅读任务产物与相关规范

按顺序阅读当前任务产物：

- `prd.md`
- `design.md`（如果有）
- `implement.md`（如果有）

```bash
sunshine task context --mode packages
```

对每个改动的包/层，阅读规范索引并按它的 **质量检查** 一节执行：

```bash
cat .sunshine/spec/<package>/<layer>/index.md
```

阅读索引里引用的具体规范文件——索引是指针，不是目标。

## 步骤 3：运行项目检查

运行项目的 lint、类型检查与测试命令。先修好失败项再继续。

## 步骤 4：对照检查清单评审

### 代码质量

- [ ] Linter 通过了吗？
- [ ] 类型检查通过了吗（如适用）？
- [ ] 测试通过了吗？
- [ ] 没有留下调试日志吧？
- [ ] 没有压制的警告或绕过类型安全的写法吧？

### 测试覆盖

- [ ] 新函数 → 加了单元测试吗？
- [ ] Bug 修复 → 加了回归测试吗？
- [ ] 行为变更 → 更新了现有测试吗？

### 规范同步

- [ ] `.sunshine/spec/` 需要更新吗？（新模式、新约定、学到的教训）

> “如果我修了一个 bug 或发现了不明显的东西，我应不应该把它记下来，让未来的我不再踩同一个坑？”→ 如果是，更新相关规范文档。

### 范围纪律

- [ ] 有没有顺手整理任务没要求的代码？
- [ ] 有没有为尚不存在的情况加抽象、配置或扩展点？
- [ ] 有没有为不可能发生的状态加推测性兜底？
- [ ] 有没有改动验收标准没提到的文件？
- [ ] 有没有在调用方加变通，而不是在行为真正所在的地方修？

## 步骤 5：跨层维度（如适用）

如果改动局限在单一层，跳过这一步。

### A. 数据流（改动涉及 3 层以上）

- [ ] 读流程是否正确追踪：Storage → Service → API → UI
- [ ] 写流程是否正确追踪：UI → API → Service → Storage
- [ ] 类型/schema 是否在层与层之间正确传递？
- [ ] 错误是否正确传播给调用方？

### B. 代码复用（改常量、建工具函数）

- [ ] 新建之前是否先搜索过已有类似代码？
  ```bash
  grep -r "pattern" src/
  ```
- [ ] 同一个值重复出现时，它是否代表一个稳定的概念、其调用方必须一起改？只有这时才抽取——今天恰好相同的两个字面量应该保持分离。
- [ ] 批量修改后，是否所有出现处都更新了？

### C. 导入/依赖（新建文件）

- [ ] 导入路径是否正确（相对 vs 绝对）？
- [ ] 没有循环依赖吧？

### D. 同层一致性

- [ ] 使用同一概念的其他地方是否一致？

---

## 步骤 6：报告并修复

报告你发现的每一个违规。然后：

- 机械与局部问题（lint 细节、缺失类型、错误导入、死分支、失败断言）→ 就地修复，然后重新运行项目检查。
- 设计或判断问题（给共享概念命名、移动模块边界、改公开接口、重新划定行为归属）→ 记录证据与你的建议，然后停下。不要悄悄重写。

如果修复会动到当前任务范围之外的文件，说明情况并停下，不要扩大改动。
