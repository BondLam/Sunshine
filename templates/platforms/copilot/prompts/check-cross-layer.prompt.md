# 跨层检查

检查你的改动是否考虑了所有维度。大多数 bug 来自“没想到”，而不是技术不行。

> **注意**：这是**实现后**的安全网。理想情况下，在写代码**之前**先读[实现前检查清单](.sunshine/spec/guides/pre-implementation-checklist.md)。

## 执行步骤

### 1. 确认改动范围

```bash
git status
git diff --name-only
```

### 2. 选择适用的检查维度

根据改动类型，执行下面相关的检查：

---

## 维度 A：跨层数据流（涉及 3 层以上时必需）

**触发条件**：改动涉及 3 层或更多层

| 层 | 常见位置 |
|-------|------------------|
| API/路由 | `routes/`、`api/`、`handlers/`、`controllers/` |
| Service/业务逻辑 | `services/`、`lib/`、`core/`、`domain/` |
| 数据库/存储 | `db/`、`models/`、`repositories/`、`schema/` |
| UI/展示 | `components/`、`views/`、`templates/`、`pages/` |
| 工具 | `utils/`、`helpers/`、`common/` |

**检查清单**：
- [ ] 读流程：Database -> Service -> API -> UI
- [ ] 写流程：UI -> API -> Service -> Database
- [ ] 类型/schema 是否在层与层之间正确传递？
- [ ] 错误是否正确传播给调用方？
- [ ] 每一层都处理了加载/等待状态吗？

**详细指南**：`.sunshine/spec/guides/cross-layer-thinking-guide.md`

---

## 维度 B：代码复用（改常量/配置时必需）

**触发条件**：
- 修改 UI 常量（标签、图标、颜色）
- 修改任何硬编码值
- 在多处看到类似代码
- 新建工具/辅助函数
- 刚完成跨文件的批量修改

**检查清单**：
- [ ] 先搜索：有多少地方定义了这个值？
  ```bash
  # 在源文件里搜索（按项目调整扩展名）
  grep -r "value-to-change" src/
  ```
- [ ] 同一个值重复出现 → 它是否代表一个稳定的概念、其调用方必须一起改？只有这时才抽取。今天恰好相同的两个字面量应该保持分离
- [ ] 修改后，是否所有使用处都更新了？
- [ ] 如果新建工具函数：是否已有类似工具？

**详细指南**：`.sunshine/spec/guides/code-reuse-thinking-guide.md`

---

## 维度 B2：新建工具函数

**触发条件**：准备新建工具/辅助函数

**检查清单**：
- [ ] 先搜索是否已有类似工具
  ```bash
  grep -r "functionNamePattern" src/
  ```
- [ ] 如果已有类似的，能扩展它吗？
- [ ] 如果新建，位置对吗（共享 vs 领域专属）？

---

## 维度 B3：批量修改之后

**触发条件**：刚在多个文件里改了类似模式

**检查清单**：
- [ ] 是否检查了所有有类似模式的文件？
  ```bash
  grep -r "patternYouChanged" src/
  ```
- [ ] 有没有漏掉应该一起更新的文件？
- [ ] 重复出现的地方是否代表一个稳定的概念、其调用方必须一起改？只有这时才抽象——不要为了预防尚未发生的重复而抽象。

---

## 维度 C：导入/依赖路径（新建文件时必需）

**触发条件**：新建源文件

**检查清单**：
- [ ] 导入路径是否正确（相对 vs 绝对）？
- [ ] 没有循环依赖吧？
- [ ] 与项目的模块组织一致吗？

---

## 维度 D：同层一致性

**触发条件**：
- 修改展示逻辑或格式化
- 同一领域概念在多处使用

**检查清单**：
- [ ] 搜索其他使用同一概念的地方
  ```bash
  grep -r "ConceptName" src/
  ```
- [ ] 这些用法是否一致？
- [ ] 它们是否应该共享配置/常量？

---

## 维度 E：范围纪律（每次都适用）

**触发条件**：每次改动，在报告完成之前

**检查清单**：
- [ ] 有没有顺手整理任务没要求的代码？
- [ ] 有没有为尚不存在的情况加抽象、配置或扩展点？
- [ ] 有没有为不可能发生的状态加推测性兜底？
- [ ] 有没有改动验收标准没提到的文件？
- [ ] 有没有在调用方加变通，而不是在行为真正所在的地方修？

---

## 常见问题速查

| 问题 | 根因 | 预防 |
|-------|------------|------------|
| 改了一处，漏了其他处 | 没搜索影响范围 | 改之前先 `grep` |
| 某层丢了数据 | 没检查数据流 | 从数据源追踪到目的地 |
| 类型/schema 不匹配 | 跨层类型不一致 | 用共享类型定义 |
| UI/输出不一致 | 同一概念在多处使用 | 抽取共享常量 |
| 已有类似工具 | 新建前没搜索 | 新建前先搜索 |
| 批量修复不完整 | 没验证所有出现处 | 改完之后再 grep |

---

## 输出

报告：
1. 你的改动涉及哪些维度
2. 每个维度的检查结果
3. 发现的问题与修复建议
